# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Assumed local naive datetime without converting UTC `punch_in` to IST (+05:30); ignored overnight shift calendar date attribution; and used integer division before comparing grace period (`int(diff / 60) > 10`), causing `09:40:01` to be treated as 10 minutes and not late. | Sending punch-in at `09:40:01 IST` returned `late_minutes = 0` instead of `10`. | Converted `punch_in` to IST, computed boundary against `record_date`, checked `diff_seconds > 600`, and floored total minutes since `shift_start` per rule R2. |
| 2 | `compute_work_hours` (lines 40–41) | Used standard Python `round()` (banker's rounding / round-half-to-even) instead of decimal round-half-up. | Work intervals like 4.545 hours rounded to 4.54 instead of 4.55. | Implemented `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)` per rules R4 and R8. |
| 3 | `POST /employees` (lines 80–99) | 1) Allowed identical `shift_start` and `shift_end`. 2) Relied on vulnerable `find_one()` check-then-insert allowing race conditions. 3) Returned internal `_id` and omitted standard `created_at` epoch timestamp. 4) Missing validation on `emp_code` regex and email. | Concurrent employee creation requests produced duplicate documents; passing equal shift times returned 201 instead of 422. | Added unique index on `emp_code` with `DuplicateKeyError` handling (yielding 409), added validation rejecting equal shifts with 422, and properly formatted response without `_id`. |
| 4 | `POST /attendance/punch-in` (lines 101–121) | 1) Did not handle overnight shifts (R1). 2) Check-then-insert caused race conditions on simultaneous punch-ins. 3) Accepted invalid status values like ABSENT/LEAVE. 4) Added an artificial `"id"` field to response. 5) Failed to convert epoch milliseconds to BSON UTC datetimes. | Simultaneous requests created duplicate punch-ins for the same day; response schema failed contract validation due to extra `"id"` field. | Created compound unique index on `(emp_code, date)` to atomically prevent duplicates with 409, implemented R1 overnight shift attribution, restricted status enum to `PRESENT`, `WFH`, `ON_DUTY`, and returned standard `AttendanceRecord`. |
| 5 | `GET /attendance` (lines 124–150) | Loaded entire collection into memory with `list(find(q))` and sorted in Python; missing secondary sort by `emp_code` ascending; did not validate `date_from > date_to`; injected spurious `"id"` field. | Severe performance degradation and OOM on 100k records; passing inverted dates returned 200 with empty list instead of 422. | Validated `date_from <= date_to` (returning 422 if invalid), used index-backed MongoDB `.sort([("date", -1), ("emp_code", 1)]).skip().limit()` for pagination, and conformed to `AttendancePage` schema. |
| 6 | Database Initialization & Lifespan | No indexes were created at startup. | Every query performed an unindexed `COLLSCAN`, failing performance and explain requirements on large datasets. | Added idempotent index creation in FastAPI `lifespan` handler covering all queries and uniqueness constraints. |

Also note anything you looked at and decided was **not** a defect, and why:
- Environment variable loading with `load_dotenv()`: The starter loaded `.env`, but real OS environment variables take precedence when `override=False`. This aligns with the assignment contract requiring injected environment variables to win.
- Naive datetime handling by PyMongo: PyMongo by default returns timezone-naive datetimes. Rather than modifying database documents, configuring `MongoClient(..., tz_aware=True)` and treating all stored instants as UTC cleanly fulfills the contract without altering stored data.
